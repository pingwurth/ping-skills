# 代码审查(claude-review)

对一次改动做多角度、相互独立的审查,再逐条验证,最终输出按严重度降序排列的 JSON 发现清单。

## 调用语法

`/claude-review [档位] [--max-findings all|default|N] [目标]`

- **档位**:`low` | `medium` | `high`(默认)| `max`
- **目标**(可选):PR 号、分支名或文件路径;缺省时评审当前分支的改动
- **--max-findings**:最终报告条数上限。`default`(缺省)= 按严重度取前 20 条;`all` = 全部;`N` = 自定义条数

用户未给参数时,用默认档位 high 与默认上限运行。无论何种方式触发,在报告开头用一行简短文字告知用户当前档位与上限设置,以及如何更改(例如 `/claude-review max`、`--max-findings all`)。这行开头语会随发现一起送达用户。

## 档位

| 档位 | 角度 | 每角度候选上限 | 验证 | 补漏扫描 | 执行方式 |
|---|---|---|---|---|---|
| low | A、B、D | 4 | 无 | 无 | 主上下文亲自执行 |
| medium | A–E(5 个查错角度) | 6 | 快速自查 | 无 | 主上下文亲自执行 |
| high | 全部 10 个 | 8 | 单票验证 | 无 | subagent,可分批并行 |
| max | 全部 10 个 | 8 | 单票验证 | 有 | 独立 subagent 并行 |

max 档以**查全率(recall)**为先:抓住每一个真实 bug。在这个级别,抓住真实 bug 比避免误报更重要 —— 漏掉的 bug 是会上线的。宁可多报。

## 通用规则

- 角度之间相互独立:不要让一个角度的结论压制另一个角度。如果两个角度因不同原因标记了同一行,两条都记录。
- 通过 Agent 工具(`subagent_type: general-purpose`)运行各角度与验证者。subagent 看不到当前会话,提示词必须自包含:写明仓库绝对路径、diff 的获取方式或要读的文件、角度任务全文、候选输出格式。
- 相互独立的调用放在同一条消息里并行发出,不要串行等待。
- 如果当前工具集中没有 Agent 工具,不要报错 —— 由你在本上下文中按顺序亲自执行每个角度(以及每次验证)。
- 若当前目录不是 git 仓库且未指定评审目标,先询问用户要评审什么。

## 阶段 0 —— 收集 diff

运行 `git diff @{upstream}...HEAD`(若没有 upstream,则依次尝试 `git diff main...HEAD`、`git diff HEAD~1`)获取待评审的 unified diff。如果存在未提交的改动,或范围 diff 为空,再运行 `git diff HEAD`,把工作区改动也纳入范围 —— 评审常发生在提交之前。

如果调用时传入了目标,则改为评审该目标:

- **PR 号**:用 `gh pr diff <N>` 获取 diff;如该 PR 已在本地检出且有工作区改动,再并入 `git diff HEAD`
- **分支名**:`git diff <基准>...<分支>`(基准默认取 main 或 upstream)
- **文件路径**:`git diff HEAD -- <paths>`

将此 diff 视为评审范围。

## 阶段 1 —— 寻找候选

运行 **10 个相互独立的发现角度**(5 个查错角度 + 3 个清理角度 + 1 个「高度」角度 + 1 个规范角度),每个角度产出至多 N 条候选(见档位表)。low/medium 档只运行表中列出的角度。

### 角度 A —— 逐行扫描 diff

逐行阅读 diff 中的每一个 hunk。然后 Read 每个 hunk 所在的整个函数 —— 被改动函数中未改动行上的 bug 也在范围内(PR 会重新暴露它们,或未能修复它们)。对每一行问:什么输入、状态、时序或平台会让这一行出错?寻找:条件写反/写错、差一错误(off-by-one)、null/undefined 解引用、漏掉 `await`、把 0 当 falsy 的判断、复制粘贴后用错变量、catch 里吞掉错误、正则元字符未转义。

### 角度 B —— 被删行为审计

对 diff 删除或替换的每一行,说出它原先维护的不变量或行为,然后在新代码中寻找该不变量在哪里被重新建立。如果找不到,那就是一条候选:被移除的守卫、被丢弃的错误处理路径、被收窄的校验、删掉的恰好覆盖真实场景的测试。

### 角度 C —— 跨文件追踪

对 diff 改动的每个函数,找到它的调用方(用 Grep 搜符号),检查改动是否破坏任何调用点:新增的前置条件、变化的返回结构、新抛的异常、时序/顺序依赖。也检查被调用方:同一 PR 里的并行改动是否让某次调用变得不安全?

### 角度 D —— 语言陷阱专家

扫描 diff 所属语言/框架的经典陷阱 —— 例如:JS 的 falsy-zero、`==` 隐式转换、闭包捕获循环变量;Python 的可变默认参数、晚绑定闭包;Go 的 nil-map 写入、range 变量捕获;SQL 注入;时区/夏令时漂移;浮点数相等比较。标记 diff 引入的任何此类实例。

### 角度 E —— 包装器/代理正确性

当 PR 新增或修改一个包装另一个类型的类型(缓存、代理、装饰器、适配器)时:检查每个方法都路由到被包装的实例,而不是绕回注册表/会话/全局对象 —— 例如,一个缓存型 provider 持有 `delegate` 字段,却通过 `session.get(...)` 而不是 `delegate.get(...)` 来解析 ID,会导致重复进入缓存或无限递归。同时检查该包装器转发了调用方实际用到的所有方法。

### 复用(Reuse)

以上角度在找 bug;本角度与接下来两个角度在改动代码中找可清理之处。标记重复实现了代码库中已有能力的新代码 —— Grep 共享/工具模块以及改动点附近的文件,并指名应改用的现有 helper。

### 简化(Simplification)

标记 diff 引入的不必要复杂度:冗余或可推导的状态、略有变化的复制粘贴、深层嵌套、遗留的死代码。指名能完成同样工作的更简单形式。

### 效率(Efficiency)

标记 diff 引入的浪费:重复计算或重复 I/O、相互独立的操作被串行执行、加到启动路径或热路径上的阻塞工作。还要标记由闭包或被捕获环境构造成的长生命周期对象 —— 它们会让整个外围作用域在对象整个生命周期内无法回收(当该作用域持有大对象时就是内存泄漏);应优先选用只复制所需字段的 class/struct。指名更省的替代方案。

### 高度(Altitude)

检查每处改动是否在正确的深度修复根因,而不是用脆弱的补丁糊住症状。在共享基础设施上层层叠加特例,是修得不够深的信号 —— 优先对底层机制做更简单、更通用的改动,而不是增加特例,并指名该改动。

### 规范(Conventions)

找出约束被改动代码的所有约定文件:用户级 `~/.claude/CLAUDE.md`(如存在)、仓库根目录的 CLAUDE.md / AGENTS.md,以及任何位于被改动文件祖先目录中的 CLAUDE.md、CLAUDE.local.md 或 AGENTS.md(某目录的约定文件只约束该目录及其下的文件)。逐个读取存在的文件,然后检查 diff 是否明确违反其中写明的规则。

只有当你能同时引用确切的规则原文和违反它的确切代码行时才标记 —— 不报风格偏好,不做含糊的「文档精神」式推断。在发现中写明约定文件路径并引用规则原文,以便报告可以引证。如果没有适用的约定文件,本角度返回空。

### 清理类候选的结构

清理(复用/简化/效率)、高度、规范三类候选用与查错角度相同的 `file`/`line`/`summary` 结构;在 `failure_scenario` 中,写明具体的代价(什么被重复、被浪费、更难维护,或违反了哪条约定文件的规则),而不是崩溃场景。当输出上限迫使裁剪时,正确性 bug 永远排在清理、高度、规范类发现之前。

## 阶段 2 —— 验证(单票,三态)

对指向同一行/同一机制的候选去重,保留失败场景最具体的那条。对其余每条候选运行**一个验证者**:给它 diff、相关文件路径和该候选(提示词同样自包含),让它恰好返回以下三者之一:

- **CONFIRMED(确认)** —— 能说出触发它的输入/状态以及错误的输出或崩溃。引用该行。
- **PLAUSIBLE(可信)** —— 机制真实存在,但触发条件不确定(时序、环境、配置)。说明什么能进一步确认它。
- **REFUTED(驳回)** —— 事实错误(代码并非那样)或别处已有防护。引用能证明这一点的行。

保留投票为 CONFIRMED 或 PLAUSIBLE 的候选。这是查全模式 —— 只要有一票非 REFUTED,发现即成立。不要因不确定而丢弃。

执行方式按档位:

- **high / max**:通过 Agent 工具派验证者,并行发出;候选极多时可按文件分组由少数验证者批量判定,但每条候选必须独立给出三态结论。
- **medium(快速自查)**:不派 subagent,由你在主上下文里对每条候选做同样的三态判定,只剔除能明确引用反证行的 REFUTED 项。

## 阶段 3 —— 补漏扫描(仅 max)

再运行**一个发现者**,扮演一名已拿到验证后清单的新鲜评审者。重读 diff 及相关函数,只寻找尚未列入清单的缺陷。不要重新推导或重新确认已有条目 —— 它的任务是找遗漏。聚焦首轮容易漏掉的:被移动/抽取的代码丢失了守卫或锚点;二线陷阱(dataclass 默认值只求值一次、`hash()` 不确定性、锁范围收窄、带副作用的谓词方法);测试中 setup/teardown 不对称;配置默认值被翻转。

产出**最多 8 条额外候选**,每条指明一个清单上还没有的缺陷,并同样经过阶段 2 验证。若无新发现,返回空结果 —— 不要凑数。

## 输出

先输出开头语(档位与上限设置,及更改方法),然后以 JSON 数组返回所有通过验证的发现,每条一个对象:

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "one-sentence statement of the bug",
    "failure_scenario": "concrete inputs/state → wrong output/crash"
  }
]
```

- 按严重程度降序排列;应用 `--max-findings` 上限,裁剪时正确性 bug 永远排在清理、高度、规范类发现之前。
- `summary` 与 `failure_scenario` 用用户的主要语言撰写;`file`、`line` 保持原样。
- 若没有发现幸存,返回 `[]`。
- 不要调用其它报告类工具 —— 本次评审的输出契约就是上面的 JSON 块(开头语除外)。
