## 总体评价

架构设计是健全的：LLM/脚本分工清晰，`entry.txt` 的人工确认关卡（`# CONFIRMED`）是全流程唯一且有效的质量闸门；`utils.py` 统一了日志与 `next_step` 输出契约；五个脚本确实只依赖 stdlib；脚本自身对目标代码库只读（所有写入都落在 `.agent/sensors-analyze/` 或显式 `--out` 路径），"绝不修改目标代码库"约束在代码层面成立。

## 一、高严重度问题

### H1. check_report 无法发现"调用点遗漏"——重复行凑数即可 PASS

**位置**：`scripts/check_report.py:103-107`（规则 1）、`scripts/check_report.py:135-144`（规则 2）

规则 1 只校验 `CSV 行数 >= len(call_sites)`，规则 2 只校验"每行能映射到**某个**调用点"。两个规则组合后，**每个调用点都被至少一行覆盖**这一真正的不变量并未被校验。

**已复现**（2026-10-12 实测）：2 个调用点（`a.js:1-1`、`b.js:1-1`），CSV 2 行全部指向 `a.js:1,1`（完全相同的两行）：

```
next_step: 校验通过 (PASS)。分析完成
EXIT=0   →   校验结果: PASS
```

`b.js:1-1` 完全遗漏却 PASS。这直接违背 `问题.txt` 第 11 条（"调用点复核——数量、非空、真的能在代码中找到，发现遗漏就补充"）中"数量"核对的本意，也违背 SKILL.md 第 189 行宣称的"CSV 行数 < call_sites 数量说明第 4 步漏写了调用点"的保障方向。

**修复建议**：

```python
covered: set[tuple[str, int, int]] = set()
# 规则 2 解析成功且命中 site_keys 时：covered.add(key)
missing = site_keys - covered
if missing:
    errors.append(f"{len(missing)} 个调用点在 CSV 中无对应行: {sorted(missing)[:10]}")
# 另建议：完全相同的重复整行 → WARNING（合法场景是一调用点多值，多值行之间至少一个字段不同）
```

同时把 SKILL.md 第 189 行的规则描述从"行数 >= 即可"更新为"每个调用点至少一行"。

### H2. rg 与纯 Python 回退结果不一致；rg 不支持的正则被静默丢弃后仍引导进入第 4 步

**位置**：`scripts/locate_call_sites.py:48-77`（`rg_search`）、`scripts/locate_call_sites.py:80-93`（`py_search`）、`scripts/utils.py:51-54`（`check_rg_available`）

三个层面的分歧，均已实测：

1. **正则方言**：`entry.txt` 中的正则是按 Python 语义写的（第 282 行 `re.compile` 先编译），但 rg 走 Rust regex 引擎。含 lookahead / lookbehind / 反向引用的正则 rg 报错（exit 2），`rg_search` 只写一行 `[WARN] rg 跳过非法正则` 然后**返回空**——该正则的所有调用点静默消失。已复现：pattern `trackEvent(?=\s*\()` 在 rg 模式下 `定位到 0 处调用点`，exit 0，`next_step` 照常引导"请进入第 4 步"；同一 pattern 在纯 Python 回退模式下能正常命中。**0 命中也没有任何脚本级拦截**（SKILL.md 第 127 行仅有 prose 提示"命中数为 0 → 回第 2 步"，脚本不执行该路由）。
2. **忽略规则**：rg 默认尊重 `.gitignore` 并跳过隐藏文件/目录；纯 Python 回退用 `root.rglob("*")`，既不读 ignore 也没有排除清单。已复现：同一夹具（无 `.gitignore`，含 `node_modules/` 和 `.agent/sensors-analyze/leak.js`）下——
   - rg 模式：`['node_modules/pkg/dist.min.js:1-1', 'src/home.js:1-1']`（跳过隐藏的 `.agent/`，但**扫了 node_modules**，因为夹具无 `.gitignore`；真实仓库有 `.gitignore` 时 rg 跳过 node_modules 而回退模式照扫）；
   - 回退模式：`['.agent/sensors-analyze/leak.js:1-1', 'node_modules/pkg/dist.min.js:1-1', 'src/home.js:1-1']`（**把产物目录里的源码后缀文件当成了调用点**，vendor 目录永远被扫入）。
   
   即同一代码库、同一次分析，有 rg 和没 rg 的机器会产出**不同的 `call_sites.json`**，后续第 4~6 步全部基于不同的事实基础，且版本 diff（第 6 步）会把环境差异误报为内容差异。
3. **`which` 依赖**：`check_rg_available` 调 `subprocess.run(["which", "rg"])`，在无 `which` 二进制的最小环境里抛 `FileNotFoundError`（被 main 的 except 吞成 exit 1"执行失败"，无有效指引）。应改用 `shutil.which("rg")`。

**修复建议**：

- `rg_search` 检测到 exit 2 时，对该 pattern **回退用 `py_search` 搜**（Python 正则已在第 282 行编译过，现成可用），并 LOG.warning 说明原因，而不是静默跳过；
- 两种模式统一排除清单：rg 加 `--glob '!.agent/**' --glob '!node_modules/**' --glob '!{dist,build,venv,.venv,vendor}/**'`，回退模式在 rglob 循环里对路径段做同样的排除判断，保证两模式语义一致；
- `n_sites == 0` 时 `next_step` 改为引导回第 2 步检查正则（与 SKILL.md 第 127 行 prose 对齐），而非"请进入第 4 步"；
- `check_rg_available` 改 `shutil.which`。

### H3. `file` 列未加引号的逗号导致 report_manager / review_report 直接崩溃

**位置**：`scripts/report_manager.py:72`（`load_csv_rows`）、`scripts/review_report.py:322-325`（DictWriter）

CSV 的 `file` 列格式本身就含逗号（`文件名:start,end`）。SKILL.md 第 174 行仅一句"字段值含逗号时用双引号包裹"提醒 LLM，一旦 LLM 第 4 步漏加引号，行字段数比表头多 1，`csv.DictReader` 把多余值放进 `restkey=None`（list 类型）：

- `report_manager.py:72`：`(v or "").strip()` 对 list 调 `.strip()` → **AttributeError 崩溃**。已复现：exit 1，日志只有裸 traceback。
- `review_report.py:322-325`：`DictWriter` 默认 `extrasaction='raise'`，写出时 **ValueError: dict contains fields not in fieldnames: None** 崩溃。已复现。
- 同一份 CSV，`check_report.py` 却能优雅报错（`file 格式非法` ERROR）——三个脚本对同一类坏输入行为不一致。

**修复建议**：三处统一用 `csv.DictReader(f, restkey="__extra__", restval="")`；发现某行有 `__extra__` 时报**友好错误**（"第 N 行字段数多于表头——file 列 `a.js:1,1` 含逗号必须加双引号"）并列入 ERROR/跳过该行，而不是崩溃。report_manager 的清理逻辑兜底：`v.strip() if isinstance(v, str) else ""`。

## 二、中严重度问题

### M1. SKILL.md 声称 extract_entries 自动做 schema 校验——代码中不存在

**位置**：`SKILL.md:75`（"extract_entries.py 在加载 sensors.json 时也会自动用 sensors.schema.json 校验，schema 不符会直接报错中止"）vs `scripts/extract_entries.py:176-185`（`load_sensors` 只检查根是 dict、有 `paradigms` 键且为 list）

已复现：一个缺 `meta`、`call_chain`、`sdk_apis`、`kind`、`location`、`category` 等大量必需字段的 sensors.json 顺利通过，exit 0 并生成 entry.txt。schema 里精心定义的 `entryFunction.required`、`data_flow` 结构等约束在运行时**零生效**（缺 `grep_pattern` 时第 283 行倒是有一个注释行兜底）。

**修复建议**（两选一）：
1. 在 `load_sensors` 里实现一个针对本 schema 的最小 stdlib 校验器（只需覆盖 `required` / `type` / `enum` / `minItems` 四种关键字即可满足本 schema 的全部约束），不符则 exit 1；
2. 若不想引入校验器，则**修正 SKILL.md** 删除该承诺。
另外 SKILL.md 第 73 行把 jsonschema 命令作为"校验"主路径展示，与 `问题.txt` 第 2 条（"不要依赖第三方包，如：jsonschema"）矛盾；且命令中 `open('sensors.schema.json')` 假设 CWD 在 skill 根目录，而各步骤实际都在目标工作目录运行，照抄必失败。CLAUDE.md 里的"stdlib 替代命令"更是只 `json.load` 两个文件——**只验证了 JSON 可解析，不验证任何 schema 约束**，却命名为"Validate sensors.json against schema"，误导性强。

### M2. report_manager 的 next_step 谎报归档结果

**位置**：`scripts/report_manager.py:299`、`report_manager.py:302`

两个问题：

1. **`--diff-only` 谎称已归档**。已复现：`--diff-only` + 无历史归档 → `next_step: 首次归档完成。已保存到 .agent/sensors-analyze/reports/sensors_20261012_152734.csv`，而 `ls reports/` 只有 `diff_report.txt` 和日志——**没有任何归档文件**。`n_changes == 0` 分支同样在 `--diff-only` 下谎称"已保存到"。
2. **归档路径用二次生成的时间戳**。第 286-293 行归档用的 `archive_path` 与第 299/302 行消息里的 `generate_timestamped_name()` 是两次独立调用，跨秒边界时消息指向一个**不存在的文件名**。应直接输出 `archive_path`。

next_step 是驱动 LLM 的唯一信号，指向不存在的文件会让流程空转一步。

**修复建议**：`--diff-only` 分支单独给消息（"仅比对完成…未归档"）；归档分支复用 `archive_path` 变量。

### M3. report_manager 早期退出路径违反 next_step 契约

**位置**：`scripts/report_manager.py:240-242`

CSV 不存在时直接 `print(..., file=sys.stderr); return 1`——**没有输出 next_step**。CLAUDE.md/SKILL.md 的契约是"stdout 仅有一行 next_step，脚本以此驱动流程"，其余四个脚本在所有路径（含异常）的 `finally` 里都保证输出，唯独这里绕过。修复：把该检查移入 try 块或补 `next_step`。

### M4. diff 报告 added / modified 双重计数

**位置**：`scripts/report_manager.py:112-146`

`added = new_sigs - old_sigs` 不看 `file` 列；`modified` 又按 `file` 分组对签名变化做配对。同一 `file` 下签名从 `{S1}` 变为 `{S1', S2'}` 时，`S1'`、`S2'` 同时出现在 added（2 行）**和** modified（1 条）里，`n_changes` 与差异报告均虚高，人工复核被重复信息干扰。修复：先按 file 分组做签名集合 diff，组内再分类（全新 file → added；消失 file → deleted；同 file 内变化 → modified）。

### M5. 动态占位符检测可被常见形式绕过

**位置**：`scripts/check_report.py:44`

`_DYNAMIC_PLACEHOLDER_RE` 只匹配 `<动态|变量|unknown|dynamic|未确定` 后跟 `:` 或 `>`。`<待定>`、`<runtime>`、`TODO`、`TBD`、`?`、`N/A`、`{{page_name}}` 等常见占位写法全部漏网，规则 3 形同虚设于这些输入。修复：至少补充 `待定|暂定|占位|runtime|placeholder` 关键词；或反向白名单（值必须能匹配代码字面量的 5.5 步比对本来就是更强的检查，可在报告中说明二者互补关系）。

### M6. locate_call_sites 的 `--exts` 是死参数

**位置**：`scripts/locate_call_sites.py:237`

`--exts` 定义并出现在 `--help`（"纯 Python 回退模式下的后缀白名单"），但解析后从未被使用——`py_search`（第 84 行）硬编码全局 `DEFAULT_EXTS`。用户传 `--exts .ts` 被静默忽略。修复：`py_search` 接受 exts 参数并传入 `args.exts.split(",")`；或删掉该参数。

### M7. report_manager 归档文件名同秒冲突静默覆盖

**位置**：`scripts/report_manager.py:41-44`、`report_manager.py:292`

时间戳精度为秒，`shutil.copy2` 静默覆盖同名文件。短时间连续两次运行（或第 6 步重跑）会覆盖上一次归档，diff 历史失真。修复：文件已存在时追加 `_1`、`_2` 后缀，或时间戳加毫秒。

### M8. sensors-analyze 无任何 CodeGraph / .codegraph 前置检查（审查请求第 3 项核对结论）

**结论**：grep 全模块无任何 `codegraph`/`MCP` 引用——**sensors-analyze 既未实现也未文档化该前置检查**。请求中描述的检查逻辑（`.codegraph` 存在性 + `mcp list` 中 codegraph connected + 缺失时提示 `codegraph install`/`codegraph init`）实际位于两个单测 skill 的 `select_worktree.py`（见 `java-unit-test-generator/scripts/select_worktree.py:32-50`），对应的是仓库根 `问题.txt` 第 3~5 条，并非 sensors-analyze 自身 `问题.txt` 的条目。当前 skill 的搜索全部基于 rg/纯 Python，不消费 CodeGraph。

**建议**：若产品预期是"sensors-analyze 也应像单测 skill 一样在启动时做 codegraph 前置检查"（例如为了加速第 1 步范式识别），需新增该检查并写入 SKILL.md 工作流第 0 步；若不是，建议在 CLAUDE.md 明确一句"本 skill 不依赖 CodeGraph/MCP"，消除与其它 skill 行为不一致带来的困惑。

## 四、按审查请求逐项结论

1. **核心脚本逻辑（五步流水线协议）**：整体遵循。五个脚本均为"所有日志进文件、stdout 仅一行 next_step"的结构，异常路径有 `finally` 兜底输出。例外：report_manager 早期退出无 next_step（M3）、`--diff-only` 谎报（M2）、locate 0 命中仍引导前进（H2）。退出码语义各脚本自洽但无统一文档（见上）。
