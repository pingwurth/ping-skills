# 提问维度章程（dimension 枚举与 dd.py 严格一致）

总则（先读这里再逐维度扫）：

- **事实 vs 决策**：能从代码库/知识库/既有文档查到的是事实，自己查（结果记 `--facts`），绝不问用户；需要用户拍板的才是问题（进台账等 frontier 问）。拿不准时先查，查完仍需取舍才是问题。
- **每题必附推荐答案**：推荐答案 = 选项 + 一句理由（"推荐异步：复用现有 Job 框架，改动最小"）。没有推荐答案的问题说明调研不足，回去查。
- **depends_on 何时挂**：只有当 A 的答案会改变 B 问什么（或 B 根本不用问）时才挂 A→B。同一轮里互相依赖的两题是违规的——B 会被 frontier 自动推到后续轮次。
- **每维度先问"跳过条件"**：逐维度过一遍，命中跳过条件就跳过（不要为不存在的关注点编问题）；`q-add` 时 dimension 必须落在下方枚举里。

维度枚举：`goal` `scope` `technical` `edge` `ui` `data-model` `api` `compat` `cache` `nonfunc` `release` `ops`

## 三大基础分支（借自 hermes grill-me）

### goal — 真实目标
- 这个需求背后要解决的真问题是什么？不做会怎样？
- 用户是谁（内部运营/外部客户/其他系统）？他们现在的替代做法是什么？
- 怎样算成功（可度量）？
- 跳过条件：用户已给出清晰可度量的目标描述。

### scope — 范围与约束
- 本期 IN / OUT 边界在哪？哪些"看起来相关"的明确不做？
- 有没有时间/团队/预算/技术栈硬约束？
- 跳过条件：需求文档已含明确 IN/OUT 且用户确认。

### technical — 技术决策
- 为什么是方案 A 不是 X？（存在真实备选时才值得问）
- 如果依赖的服务/组件挂了会发生什么？降级路径是什么？
- 最坏情况是什么（数据量 100x / 并发 100x）？到什么量级必须换方案？
- 仓库里有没有既有模式可复用？（先自查——有则问题变成"复用 X 还是有理由偏离"）

### edge — 边界与异常
- 用户做 Z（重复提交/中途取消/并发操作同一资源/传非法值）会发生什么？
- 依赖方超时/返回脏数据/半成功时怎么处理？
- 有没有安全影响（越权/注入/敏感数据落日志或导出文件）？

## 设计特有维度

### ui — UI 与页面交互
- 页面/组件清单？每个的关键状态（加载/空/错误/无权限）长什么样？
- 关键交互的反馈闭环（点击后等多久、失败怎么提示、能否重试）？
- 权限差异在 UI 上如何体现？
- 跳过条件：纯后端/库/工具类项目（manifest 停用 ui 节）。

### data-model — 数据模型
- 新增/修改哪些表？每张表的归属边界（谁写谁读）？
- 既有表加列的迁移与回滚怎么做？
- 数据量级与增长（决定索引与分表）？
- 跳过条件：不落库的纯计算/转换特性。

### api — 接口设计
- 对内/对外接口清单？同步还是异步（轮询/回调/长连接）？
- 契约变更如何通知调用方？
- 错误码与重试语义（幂等吗）？
- 跳过条件：无新接口且不改动既有契约。

### compat — 兼容性
- 既有调用方/数据格式/行为的兼容策略（严格兼容/双写过渡/破坏性变更）？
- 新旧版本共存期多长？共存期数据怎么对齐？
- 跳过条件：全新独立特性，无既有调用方。

### cache — 缓存
- 缓存什么（读多写少的热点）？键规约与 TTL？
- 失效策略（写穿透/延迟双删/定时刷新）？一致性级别要求？
- 缓存击穿/雪崩的防护？
- 跳过条件：无缓存层或特性与读热点无关（manifest 停用 cache 节）。

### nonfunc — 非功能
- 容量估算（QPS/行数/存储）？性能预算（P99）？
- 安全面（鉴权/越权/敏感数据）？
- 可观测（关键指标/告警阈值）？
- 跳过条件：几乎不适用（内部小工具可降为一句话）。

### release — 灰度与回滚
- 要不要灰度开关？分级放量节奏？
- 回滚步骤（代码/配置/数据各怎么回）？
- 跳过条件：库类项目、无线上服务（manifest 停用 release 节）。

### ops — 部署与配置
- 部署形态有变化吗（新进程/新依赖/新中间件）？
- 新增配置项及默认值（谁运维、怎么改）？
- 跳过条件：部署形态与配置面零变化。

## Pitfalls（提问时的自我检查）

1. 别问依赖顺序错乱的问题（B 依赖 A 的答案时，B 进后续轮次——frontier 会自动处理，别手动乱序）。
2. 别跳过代码库直接问（"Skipping the codebase" 是最大反模式：仓库里已有的答案去问用户，用户会失去信任）。
3. 用户答"不知道"时，给选项和权衡而不是空转（此时 often 该回 technical 维度自查事实）。
4. 拷问期间不写实现代码（本 skill 全程不写生产代码）。
5. 别太顺从（"everything looks fine, look harder"）：每个维度真扫过再放行，而不是走过场。
6. 跟随用户语言（中文问中文记）。
