# UML 图规约（mermaid 内嵌 markdown）

## 选型表：哪种逻辑用哪种图

| 逻辑类型 | 图型 | 例 |
|---|---|---|
| 流程/编排/分支判定 | `flowchart TD` | 请求处理主流程、审批流 |
| 跨模块/跨系统调用时序 | `sequenceDiagram` | 前端↔API↔任务↔存储 的协作 |
| 领域模型/类型关系 | `classDiagram` | 聚合根与值对象 |
| 状态机/生命周期 | `stateDiagram-v2` | 订单状态、任务状态机 |
| 数据库表关系 | `erDiagram` | 表间外键与基数 |

明确不用 mindmap / gantt / pie / gitGraph 承载逻辑设计（check 门禁图类型白名单会 FAIL）。

## 风格规约

- **图前一句引导**：这张图回答什么问题（"下图说明导出任务从创建到终态的状态流转"）。
- **图后一句结论**：读者该从中带走什么（"失败最多重试 3 次后终态 FAILED"）。
- 节点 id 用 ascii（`A`、`SVC`、`T_TASK`），**标签用中文**：`A[异步任务]`。
- 相关角色/阶段用 `subgraph` 分组；flowchart 主方向 `TD`（步骤多而窄优于宽而扁）。
- sequenceDiagram 参与方 ≤6；超过先拆图或合并次要参与方。
- 边上标注关键条件/事件（`RUNNING --> FAILED: 失败(重试≤3)`）。

## 复杂度上限（与 dd.py check WARN 阈值一致）

- 单图 ≤15 节点、≤25 边（脚本粗估，超限 WARN 不 FAIL）。
- 超限就拆：一个子域一张图，每张图只回答一个问题。
- 一份设计文档至少核心逻辑节配一张图；全是文字的核心逻辑说明通常意味着没想清楚。

## 与"不堆砌代码"的边界

- 接口设计：表格 + 一行签名，不写实现体。
- 数据库设计：表结构表格 + erDiagram，不贴整段 DDL（索引/字符集等关键约束写进表格说明列）。
- 算法必要处可用 ≤10 行伪代码 + 一句说明；除此之外禁止出现实现代码。
- 判断标准：文档是给"要实现的人"看的契约，不是实现本身——看图能懂意图，看表能懂边界。
